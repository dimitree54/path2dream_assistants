Этот документ описывает алгоритм того, как нужно рассуждать. Он содержит логику декомпозиции сложного продукта на набор вложенных сервисов.

То есть идея в том, что у нас есть какой-то user flow. Мы его формулируем как единый сервис высокого уровня, обозначаем, какие у него входы и выходы, и таким образом можем его, затем, композировать на последовательность других более простых сервисов.

Таким образом, мы создаем иерархию различных сервисов 

Вот, идея в том, что у нас основная такая абстракция — это сервис. Декомпозируя его, мы доходим до определенного уровня, после которого можем делегировать его реализацию агенту. То есть каждый модуль имеет свою единую ответственность и тесты того, как он реализует эту ответственность, а также фиксированные интерфейсы.

Договорившись о таком контракте для каждого сервиса, мы можем уже не так акцентировать внимание на его реализации, как на том, как это все реализовано. Используя эту абстракцию сервисов, мы будем управлять сложными системами, при том что каждый из этих модулей будет управляться отдельным агентом.

Таким образом, мы не будем знать, как он реализован; мы только определяем контракты и, соответственно, используем их 

# Ideology
These "services" are less like a programming architeccture, it is semi-formal human readable contracts. They should be described simple, so a non-programmer can easy understand them, the purpose of each service. The target user is Product manager who can thinks in terms of modules bringin some value, how the module split on sub-modules and value of each of the sub-modules. But not too deep, not becoming too technical and diving into implementation details.

Product manager can describe exact requirements for each service.

On the other hand, each service documentation contains formal contract, so the developer who implements the module - implements these interfaces, so developers making different modules can use other modules.

We are writing these docs for HUMAN, not for AI or for developer, so it should be short, minimal, without too much details, only important info.

So here "service" is not a service programming pattern, it is an abstraction for easy formulation of the development task by non-programmer. For easy decomposition of services.

To keep docs easy-readable, keep them short. Do not document obvious requirements. Do not duplicate the same requirmeent several times in different words

# Tags

Each service may be marked with a tag (in a properties):
- entrypoint: special tag to mark the top level services that will be run directly by user
- interface: files that describe generic interfaces, without exact implementation details
- implementation: implementation of interfaces

Important:
- Interface doc should not know about its implementations or users
- Implementation doc should not duplicate requirements of the interface it implements. Keep the implmenetaion doc containing ONLY this implementation details, not duplication of requirements. It is needed for single source of truth in case of requirements changes.

# How to document each service you extracted

То есть, при разбиении ты для каждого сервиса создаешь какой-то такой файл документации, который, соответственно, будет ссылаться на другие файлы документации других сервисов.

В этом файле прописываешь, какие у него точные интерфейсы с типами и текстовое описание, что вообще это за единая ответственность этого сервиса, сформулированная.

Может быть, в документации будут какие-то идеи, как тестировать этот сервис. Но такая не очень длинная, но главное — сформулировать интерфейс и то, что делает этот сервис

# Declaring models
А если сервису нужно объявить какие-то модели для того, чтобы общаться с другим сервисом, то есть какие-то общие модели, которые используются в нескольких сервисах, например, для передачи данных, для возврата данных, то всё это должно быть также объявлено в отдельных файлах.

Это является частью интерфейсов, типизации.

И нужно объявить все эти модели в отдельном модуле с моделями, предположительно используя Pydantic.  ну то есть в примере выше, соответственно, слово и переведённая пара слов — это были бы как раз моделями, вынесёнными в отдельный модуль, который все вот эти сервисы используют 

# Split init interfaces and runtime
Docs should explicilty split things that are configured single time per service and passed on each call.  на примере сервиса для перевода текста: входной язык и выходной язык — это параметры инициализации. Их не нужно передавать при каждом вызове.  

Непосредственно текст, который переводится, — это то, что передаётся в runtime. Соответственно, нужно минимизировать объём данных, передаваемых в runtime.  

Если сервису нужна какая-то конфигурация, она задаётся на этапе инициализации (init time).  

Нужно явное разделение в интерфейсах: какие конфигурации есть у сервиса и что передаётся в runtime. При этом runtime-интерфейс должен быть максимально простым и понятным. 

So we try to keep interfaces minimal. Especially runtime. The service should have not too much interface methods, be simple. If it seems complex, probably it needs further decomposition.
